# Design — metrics hook surface and trace-correlated logs

## Context

Issue #142 asks for the two remaining observability pillars (metrics, trace-correlated logs) and leaves the mechanism open: "a metrics hook surface (counter and histogram callbacks or an exported registry — follow what the spec decides; no hard prom-client dependency)". The spec's `Prometheus metrics` and `Structured JSON logs with trace correlation` requirements commit to an outcome but not a mechanism.

## Decisions

- **Metrics: a pull-based `postel.metrics()` snapshot, not a push-callback config surface.** Rejected an `observability.metrics` callback (mirroring `observability.logger`) because two of the six metrics — `webhook_send_total` counted per attempt-outcome and `webhook_attempt_success_ratio` — are naturally derived aggregates (a ratio over accumulated counts), and `webhook_outbox_depth` is a point-in-time storage read, not an event. Forcing all six through one push-callback shape means either the callback fires on every attempt with a recomputed ratio (wasteful — most scrapes are 15-60s apart, most attempts are not) or the design grows two different callback shapes (event-driven vs. polled) that the issue didn't ask for. A single `postel.metrics(): Promise<MetricsSnapshot>` method — added next to the existing `postel.health()` on `LifecycleApi` — keeps one shape: cheap counters/histograms accumulate in memory from the same `attempt` / `dead-letter` runtime events `observability.logger` already taps, and `webhook_outbox_depth` / `webhook_endpoint_circuit_state` are read from storage (respectively `countPendingByTenant()` and a paginated `endpoints.list()` walk — see below) only when a snapshot is actually requested. No new config field, no new dependency, no background timer.
- **In-memory counters always accumulate; no opt-in gate.** Unlike `observability.logger` (opt-in, since forwarding is observable side-channel work a host must ask for), the metrics registry's bookkeeping is a handful of `Map` increments per event — negligible next to an HTTP dispatch — so it always runs and `postel.metrics()` is always safe to call, even if the host never scrapes it. Simpler than threading an enabled/disabled flag through the dispatch pipeline for a cost that doesn't need gating.
- **`webhook_endpoint_circuit_state` is pulled from `endpoint.state` at snapshot time, not tracked from `circuit-open`/`circuit-close` events.** `CircuitBreakerRegistry.isOpen()` auto-closes a breaker once its cooldown elapses (persisting `endpoint.state` back to `active`) as a side effect of the *next* dispatch attempt's pre-check, before `recordOutcome()` runs — so the orchestrator's own `circuit-close` event never fires on that (the common) path; only `recordOutcome()`'s own, narrower `wasOpen` transition would emit it, which the pre-check already short-circuits in normal single-process operation. Rather than build a gauge that reliably reads `1` but usually gets stuck there, the gauge reads the same persisted `endpoint.state` the registry itself treats as the cross-process authority (`sender/retry/circuit.ts`'s `reconcile()`), via a paginated `storage.endpoints.list()` walk at snapshot time — consistent with `webhook_outbox_depth`'s pull-based `countPendingByTenant()` read, and correct regardless of which internal path performed the close.
- **`AttemptPayload` gains `tenantId` and `latencyMs`; `DeadLetterPayload` gains `tenantId`.** Both are additive (existing consumers destructure only the fields they use); needed because the metrics registry labels `webhook_attempt_duration_seconds` / `webhook_attempt_success_ratio` / `webhook_dead_letter_total` by `tenant_id` and observes latency for the duration histogram, and the retry orchestrator already has the message's `tenantId` and the dispatch outcome's `latencyMs` in scope at the point it emits both events.
- **`webhook_attempt_success_ratio` counts `success` / `filtered` / `skipped` as success**, matching the orchestrator's own `success` classification used for circuit-breaker outcome recording (`sender/retry/orchestrator.ts`) — one definition of "success" for both circuit state and this ratio, not two.
- **Trace correlation rides the existing logger pass-through, not a new JSON writer.** The spec's literal text ("the library SHALL emit structured JSON logs") could be read as Postel owning a `console.log(JSON.stringify(...))` call, but the sibling `Logger pass-through for runtime events` requirement already established the pattern (PORT-SPECIFIC: forward runtime events to a host-supplied callback; the host's own logger — pino, winston, whatever — owns JSON serialization). Adding a `trace_id` field to the same forwarded `LogEvent` gets "logs and traces can be correlated" without Postel taking on log formatting, transport, or levels it doesn't own today. `tracing.ts` already lazily loads `@opentelemetry/api` and caches the resolved module; a synchronous `getActiveTraceId()` reads `trace.getActiveSpan()?.spanContext().traceId` off that cached module, so the logger-wiring code (already synchronous) can attach it with no new async boundary.
- **`GET /admin/health` reuses the existing authorize gate — no unauthenticated bypass.** The health-check requirement's "safe for load-balancer probes" framing might suggest an unauthenticated fast path, but adding one inside `@postel/admin`'s router means special-casing the router's default-deny posture (`Admin HTTP handlers`'s own scenario: "every request is rejected with 403 before any outbound call runs") for exactly one route — a security-relevant carve-out the issue doesn't ask for. A host that wants a fully unauthenticated LB probe endpoint already can: call `postel.health()` directly from its own infra route, unrelated to the admin router. `GET /admin/health` is for ops tooling that already authenticates against the admin router, giving it the same gauges over HTTP that `postel.health()` returns directly.

## Non-Goals

- Prometheus text-exposition format (`# TYPE ...` / `# HELP ...` lines). `postel.metrics()` returns structured data; mapping it to `prom-client` `Gauge`/`Counter`/`Histogram` objects or raw exposition text is the host's five-line job, shown in the docs recipe.
- Retention/pruning metrics or alerting — out of scope per the issue.
- An unauthenticated health-probe route — see decision above.

## Risks / Trade-offs

- *Risk:* `postel.metrics()`'s in-memory registry resets on process restart, so a host scraping it into Prometheus sees counters reset to 0 rather than Prometheus's usual "restart-safe" `_total` convention with an OpenMetrics `# TYPE ... counter` reset marker. → *Mitigation:* this is standard behavior for any in-process counter (Prometheus client libraries have the same property); documented in the recipe, not treated as a defect.
- *Risk:* `webhook_attempt_duration_seconds` exposes `count`/`sum` (for computing an average) rather than fixed histogram buckets. → *Mitigation:* the spec text names the metric, not a bucket layout; `count`/`sum` is what `postel.metrics()` can produce without adopting a bucketing scheme the issue never specified, and a host wanting real Prometheus histogram buckets can bucket the raw per-attempt values itself via `observability.logger`'s `attempt` events (which already carry latency once wired for metrics — see tasks).
